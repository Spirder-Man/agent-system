## 0. 前提条件（先读完再动手）

不同角色环境不同。**不要用开发机标准去验收 GPU 全栈，也不要用 GPU 机标准去要求只看 UI 的贡献者。**

### 0.1 三种角色

| 角色 | 要做什么 | 不需要做什么 |
|---|---|---|
| **使用者（推荐路径）** | `git clone` + 拉发布镜像 + 本机挂载 GGUF | 编译 llama.cpp、提交 Git、装 .NET SDK |
| **贡献者 / 无 GPU 开发** | 跑 demo compose 或前端 mock、单元测试 | NVIDIA 卡、完整国标语料 |
| **维护者（打镜像 / 打离线包）** | 在能访问镜像仓库的机器上 `docker build` 并 push | 把 devel 镜像和 `.gguf` 推进 Git |

### 0.2 系统环境

| 项 | 使用者（GPU 全栈） | 使用者（无 GPU 演示） | 维护者打 CUDA 镜像 |
|---|---|---|---|
| 操作系统 | Windows 10/11 22H2+（WSL2）或 Ubuntu 22.04/24.04 x86_64 | 同上 | **Linux x86_64 更稳**；Windows 也能编但慢、易 OOM |
| CPU | x86_64，建议 4 核以上 | 4 核以上 | 8 核以上更舒服 |
| 架构 | 仅 amd64。不承诺 ARM / Apple Silicon GPU 直通 | amd64 或能跑 Docker 的本机 | amd64 |
| 权限 | 能跑 Docker；Windows 上 Web 用 `8088` 可免管理员 | 同左 | 能 `docker login` 目标仓库 |

不支持作为一等公民：32 位系统、仅 CPU 却强行 `docker-compose.yml` GPU `deploy.devices`、未开 WSL2 的旧版 Docker Toolbox。

### 0.3 硬件环境

| 场景 | 内存 | 磁盘（可用） | GPU / 显存 |
|---|---|---|---|
| 只跑 demo（Postgres + API，无 llama） | ≥ 8 GB | ≥ 10 GB | 不需要 |
| CPU llama 栈（8B Q4，`-ngl 0`） | ≥ 16 GB | ≥ 30 GB（含模型） | 不需要 |
| GPU：仅 8B + embed | ≥ 16 GB | ≥ 40 GB | NVIDIA，约 **8 GB** 显存 |
| GPU：8B + Qwen2.5-VL 同卡（推荐验收 / 生产） | ≥ 16 GB，建议 32 GB | ≥ 50 GB | NVIDIA，**建议 24 GB**（3090 或 **4090 约 25GB**） |
| 维护者编译 `Dockerfile.llama` | ≥ 16 GB，建议 32 GB | ≥ 40 GB（devel 层很大） | 编译可用 stub，**不强制有卡**；跑起来才要卡 |

磁盘构成粗算：发布运行镜像合计约 5–6 GB；GGUF 四件约 8B ~4.8 GB + embed ~0.3 GB + VL ~5.7 GB + mmproj ~1.3 GB。

驱动：

- 宿主机必须有 **NVIDIA 驱动**，`nvidia-smi` 能列出 GPU。
- Linux 还需 **NVIDIA Container Toolkit**，使 `docker run --gpus all` 成立。
- Windows：Docker Desktop **WSL2 后端 + 启用 GPU**。驱动装在 Windows 上，不是拷进镜像。
- **不需要**在宿主机再装一份 CUDA Toolkit；CUDA 在镜像里。

### 0.4 软件环境

**使用者（compose 跑栈）**

| 软件 | 版本口径 |
|---|---|
| Git | 能 clone Gitee |
| Docker Engine 或 Docker Desktop | 建议 24+；Compose V2（`docker compose`） |
| 浏览器 | 访问 Web（默认 `80` 或 `8088`） |

**贡献者（改代码）额外需要**

| 软件 | 版本口径 |
|---|---|
| .NET SDK | 8.0.x |
| Node.js | 与 `agent1-web/package.json` 一致（建议 20 LTS） |
| 可选 | `dotnet test`、前端 `npm test` |

**维护者（发布镜像）额外需要**

| 软件 | 用途 |
|---|---|
| 能登录的容器仓库账号 | Gitee 容器镜像 或 GHCR |
| 构建机 Docker | `docker build` / `docker push` |
| 可选 CI | 当前 [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) 在 **GitHub** 上跑单测；Gitee 默认推送 **不会**自动编 CUDA 镜像，需另配或手动打 tag 再编 |

### 0.5 网络环境

| 路径 | 必须能访问 | 失败时的后果 |
|---|---|---|
| 使用者主路径 | Gitee（源码）+ 容器仓库（pull 业务镜像）+ Docker Hub 或国内镜像加速（`pgvector/pgvector:pg16` 等） | 改走「离线 Release 包」 |

| 另一台机完全不能访问 Docker Hub | — | **不要**在那台机 `docker pull nvidia/cuda`；用离线运行 tar，或在有网机构建好再拷 **运行镜像** |

说明：

### 0.6 端口（默认，均可被 `.env` 覆盖）

## 1. 目标形态：三种产物、三个地方

```text
使用者
  ├─ git clone          →  Gitee Git（源码 + compose + 文档）
  ├─ docker compose pull →  容器仓库（api / web / llama-cuda 带 libllama.so）
  └─ 下载或拷贝          →  models/*.gguf + knowledgebase/（卷挂载，不进镜像）
```

| 产物 | 存放 | 进 Git？ |
|---|---|---|
| 源码、Dockerfile、compose、CI、文档 | Gitee `agent-system` | 是 |
| `agent1-llama-cuda`、`agent-system-api`、`agent1-web` 的 **版本 tag 镜像** | Gitee 容器镜像或 GHCR | 否（二进制在仓库网页，不在 git 对象里） |
| GGUF、完整法规语料 | ModelScope / HF / Release 附件 / 自备目录 | **否**（已 `.gitignore`：`models/`、`*.gguf`） |
| `nvidia/cuda` devel、本机 `docker save` 的 10GB 编译链 | 仅维护者磁盘 | **否** |
| 大赛 U 盘 `容器化部署/` | 可选 Release `offline-gpu.zip` | **否**（独立分发，不是第二套源码仓） |

原则：**Git 只放能 diff 的文本；能跑的层放镜像仓库；大文件放模型站或挂载目录。**

## 2. 与现状的差距

| 现状 | 问题 | 落地后 |
|---|---|---|
| `docker compose` 默认 `build: Dockerfile.llama` | 用户首次要编 CUDA、拉 GitHub llama.cpp | 默认 `image: <registry>/agent1-llama-cuda:<tag>` |
| `容器化部署/gpu/images/*.tar` 手拷 | 旧 llama tar 缺 `libllama.so`；devel 过大 | 维护者编好再 `save` **仅运行镜像**；或用户 `pull` |
| 模型在旁路 `cpu/models` | 对大赛合理，对 clone 用户不发现 | `scripts/download-models` + `MODELS_PATH=./models` |
| CI 只在 GitHub 跑单测，且 `on.branches` 已含 `master` | Gitee 默认推送不触发该 workflow | 对齐分支名已做；Gitee Go 另配；CUDA 构建用 tag 手动/夜间任务 |
| 根 README 已写 GPU 优先、模型自备 | 未写镜像仓库地址与 tag 约定 | 本文 §3、§6 补齐后链到 README |

已在源码仓落地的修复（`4e5b6e8`）：CUDA 运行镜像收集 `.so` 并 `ldconfig`。这是 **维护者编镜像** 的正确配方，不是让每个用户在评委机上现场编译。

建议命名（与现有 compose 服务对齐）：

| 镜像 | 建议 tag 形态 | 内容 |
|---|---|---|

完整引用示例（占位，选定后全局替换）：

```text
registry.gitee.com/liuchao_yue/agent-system/agent1-llama-cuda:0.1.0
```

或：

```text
ghcr.io/<org>/agent1-llama-cuda:0.1.0
```

规则：

- **语义化版本**与 Git tag 一致：`git tag v0.1.0` ↔ 镜像 `:0.1.0`。
- 另打 `:latest` 仅指向最新稳定，文档仍钉死数字版本，避免评测不可复现。
- llama 镜像必须含 `libllama.so` / `libggml*.so`（或静态链上等价物）。验收：`ldd llama-server` 无 `not found`，容器不再 exit 127。

- `nvidia/cuda:12.4.0-devel-ubuntu22.04`
- `nvidia/cuda:12.4.0-runtime-ubuntu22.04`
- `ubuntu:22.04`（CPU llama）

## 6. 维护者：如何「把需要的上传上去」

在一台 **能访问 GitHub + NVIDIA CUDA 基础镜像 + 目标容器仓库** 的机器上（满足 §0.3–0.5 维护者列）。

### 6.1 构建并推送业务镜像

```bash
cd agent-system
# 确认 Dockerfile.llama 会收集 .so（勿再只 COPY llama-server 单文件）

docker compose -f docker-compose.yml build llama-server api web
# 三个 llama 服务共用 agent1-llama-cuda

docker tag agent1-llama-cuda:latest  <REGISTRY>/agent1-llama-cuda:0.1.0
docker tag <本机构建的 api 镜像名>   <REGISTRY>/agent-system-api:0.1.0
docker tag agent1-web:latest         <REGISTRY>/agent1-web:0.1.0

docker login <REGISTRY>
docker push <REGISTRY>/agent1-llama-cuda:0.1.0
docker push <REGISTRY>/agent-system-api:0.1.0
docker push <REGISTRY>/agent1-web:0.1.0
```

推送前自检：

```bash
docker run --rm --entrypoint sh <REGISTRY>/agent1-llama-cuda:0.1.0 -c \
  "ldd /opt/llama/bin/llama-server | grep -i 'not found' || echo OK"
```

无 `libllama.so => not found` 再 push。

### 6.2 源码

```bash
git tag v0.1.0
git push origin master
git push origin v0.1.0
```

只推 Git 对象：代码与文档。不推 `images/*.tar`。

### 6.3 可选：离线包（给断网评委机）

在刚编好的机器上：

```bash
docker save <REGISTRY>/agent1-llama-cuda:0.1.0 -o agent1-llama-cuda-0.1.0.tar
docker save <REGISTRY>/agent-system-api:0.1.0 -o agent-system-api-0.1.0.tar
docker save <REGISTRY>/agent1-web:0.1.0 -o agent1-web-0.1.0.tar
docker save pgvector/pgvector:pg16 -o pgvector-pg16.tar
```

打 zip：**仅这 4 个运行 tar** + 对应 `docker-compose` + `load-images` 脚本。  
**不要**打进 `nvidia-cuda-*-devel*.tar`、`agent1-cuda-devel-build*.tar`。

模型仍用 `cpu/models` 或同包 `models/` 目录，与镜像分开。

上传位置：Gitee/GitHub **Release 附件**（注意体积限额）或网盘链接写进 Release 说明。

## 7. 使用者：三种启动路径

### 7.1 能上网 + 有 NVIDIA GPU（长期主路径）

满足 §0.2–0.5「使用者 GPU」。

1. 安装 Docker，验证：`docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi`  
   （若 Docker Hub 不通，这条会失败，改用已 load 的 base tar 或跳过该探测、直接看 `nvidia-smi`。）
2. `git clone` → `cp .env.example .env` → 填写密码与 `MODELS_PATH`。
3. 下载四件 GGUF 到 `MODELS_PATH`。
4. `docker compose pull && docker compose up -d`（待 compose 改为 image 后）。
5. 打开 `http://localhost:${WEB_PORT}`。健康：`curl http://localhost:5000/health/live`。

### 7.2 无 GPU

`docker compose -f docker-compose.demo.yml up -d`，`LLM_OPTIONAL=true`。不测 8083、不测真 8B 推理。

### 7.3 断网 / Docker Hub 不可达

1. 解压 §6.3 离线包，`load-images`。  
2. 不要 `rebuild-llama.ps1`（那是缺库时的补救，需要 devel 与编译）。  
3. 模型用 U 盘拷到 `MODELS_PATH`。  
4. `docker-up`。

若离线包里的 llama tar **仍**报 `libllama.so ... No such file`，说明该 tar 还是旧构建；回到有网机构建 §6.1，不要在评委机现场编 CUDA。

### 7.4 llama.cpp 钉 **b5512**（工作区目标；须在 4090 冒烟后再 save）

上游 PR #12898（`--mmproj` / libmtmd）落在 **b5331**。tools+stream 约 **b5478** 打开，随后 #13786 修 streaming 崩溃。**本机工作区** CUDA / CPU Dockerfile 钉 **b5512**（D01 + D03 构建目标）。`docker-compose.yml` 里 `llama-vision` 传 `--mmproj` 的写法本来就对；旧 b5092 的 `llama-server` 不认该参数才会 `invalid argument: --mmproj`。

Dockerfile 钉 **b5512** 是构建目标，不是「已在 4090 用该 Dockerfile 重编」。远端曾停留在 `4e5b6e8`：当时只把 `libllama.so` 打进运行镜像，Dockerfile 仍钉 b5092。本仓 Dockerfile 已改钉 **b5512**。RTX 3070 于 2026-09-05/06：第一波 exit 127；第二波主 LLM/embed 起来，vision 仍拒 `--mmproj` ×43。飞致云 4090 于 2026-09-07/08 跑通的是仓库外离线包 / 自定义镜像（vision healthy、`gpu-quick` 过、`gpu-full` 未过）。标 `0.1.0-b5512` 的生产 tar 仍须用本仓 Dockerfile 编出并做最小冒烟后再 `docker save`。`--mmproj` 与 D03 尚未作为该钉版的正式发布结论；`gpu-full` 本轮未通过。

**硬件与启动：** 8GB 卡（3070）装不下 8B + VL 同卡；「8B+VL 同卡」要 ≥24GB（3090 / 4090）。compose 里 `ENABLE_VISION_OCR` **默认 false**（L11：裸 `up -d` 不启 vision）。生产 4090 **只用** `scripts/docker-up`：`.env` 未显式设置时按 `nvidia-smi` 最大显存决定，≥20000 MiB 开视觉并点名起 `llama-vision`。4090 不要在 `.env` 写 `ENABLE_VISION_OCR=false`。要强制开关：在 `.env` 写 `true|false` 再跑 `docker-up`。

4090 冒烟通过后再：

```text
docker save agent1-llama-cuda:latest -o agent1-llama-cuda-0.1.0-b5512.tar
```

覆盖离线包 `images/agent1-llama-cuda.tar`。不要用包内 `rebuild-llama.ps1` 当生产钉版（`COPY llama.cpp/` 仍是包内旧源码）。`docker-compose.release.yml.example` 仍禁止 pull，冒烟后再谈 `:0.1.0` push。

## 8. 分阶段落地清单

### 8.0 现在就能做 vs 必须 GPU 冒烟再上传

| 打 Git tag `v0.1.0` 并写「GPU 全栈可用」 | **不要在 `gpu-full` 未过时打** | 4090 `gpu-quick` 过、`gpu-full` 未过。tag 会被当成可复现发布 |

GPU **最小冒烟**（挡住上次事故即可，约半小时，不是整本手册）：

1. 用当前 `Dockerfile.llama`（含 `.so` / `ldconfig`）编出新镜像，或 load 刚 `docker save` 的新 tar。  
2. `docker compose ps`：`llama-server` / `llama-embed` **Up**，无 restart / exit 127。4090 生产必须再有 `llama-vision` **Up**，无 `invalid argument: --mmproj`，无 `Cannot use tools with stream`（不要只看「不再 127」）。  
3. `curl` LLM `:8080`、embed `:8081` 通；4090 再打 `:8083`。API 不再报 `llama-embed:8081 Name or service not known`。  
4. 问一句会走 LLM 的合规（不要只用 `benzene` 快路径）。  
5. 通过后再 `docker save agent1-llama-cuda:latest`；否则可标「VL / D03 未验收」，**不要**当生产 tar。


## 9. 验收标准
